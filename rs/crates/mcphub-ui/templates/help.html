Connecting your MCP client

Point your client at this gateway's /mcp endpoint. It will discover how to sign you in automatically and open a browser for OAuth — you don't paste a token, and there is no static API key to leak.

Server URL: {{ chrome.mcp_url }}

Claude Code

claude mcp add --transport http mcphub {{ chrome.mcp_url }}

Or in .mcp.json:

{
  "mcpServers": {
    "mcphub": { "type": "http", "url": "{{ chrome.mcp_url }}" }
  }
}

The transport must be http. sse and streamable-http will not connect.

Claude Desktop

Settings → Connectors → Add custom connector, then enter {{ chrome.mcp_url }}. A browser window opens for sign-in the first time.

Codex

codex mcp add mcphub --transport http {{ chrome.mcp_url }}
codex mcp login mcphub

ChatGPT app

Settings → Connectors → Add, then enter {{ chrome.mcp_url }} and complete the sign-in prompt.

Checking it worked

Ask your client to list its tools. You should see everything in Catalog that you've been granted — no more, no less. If a tool you expect is missing, check My access, then your profile with get_profile.

If it won't connect

  • The browser never opens — the client is almost certainly using the wrong transport. It must be http.
  • Sign-in succeeds but no tools appear — you're connected and authenticated; you just have no grants yet. Request access from Catalog.
  • TLS or certificate errors — your machine doesn't trust the gateway's certificate. That's a trust-store problem on your side, not a sign-in problem.
  • Some servers use their own port. If an admin told you a server has a dedicated port, use that URL instead — it signs you in against that server's own identity provider.

Managing your own access

Two separate things decide whether you can call a tool, and both must allow it:

Grants vs profiles
LayerWho changes itWhat it does
Grants An admin What you are permitted to call at all. See My access.
Your profile You Your own narrowing on top. You can switch an MCP server off, or limit which of its functions you expose.

A profile can only ever take access away, never add it. Disabling something in your profile hides it; enabling it again only restores access you were already granted. If a tool isn't in My access, no profile change will make it callable — request access instead.

Turning an MCP off removes its tools from both your tool list and from being callable. There is no state where a tool is hidden but still works, or visible but blocked by your profile.

The self-service MCP

You change your profile by calling tools, not through this portal — the same way your agent calls anything else. The server is called self-service and it goes through exactly the same security checks as every other MCP server.

Self-service tools
ToolWhat it does
list_available_mcpsWhich MCP servers you can use
get_profileYour current profile
enable_mcpTurn an MCP server back on for yourself
disable_mcpTurn an MCP server off for yourself
list_functionsWhich functions of an MCP are enabled
enable_functionAllow one function
disable_functionRestrict to an explicit allowlist without that function

Turning an MCP off

{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "disable_mcp", "arguments": {"mcp_name": "demo-echo"}}}

Its tools disappear from your tool list immediately. enable_mcp brings them back.

Restricting individual functions

{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "disable_function",
            "arguments": {"mcp_name": "demo-echo", "function_name": "delete_thing"}}}

Note: an MCP starts unrestricted (every granted function allowed). The first disable_function switches it to an explicit allowlist — so it narrows to nothing rather than to "everything except that one". Use enable_function to add back the ones you want, and list_functions to check where you stand.

You cannot lock yourself out

Disabling self-service in your own profile is refused, as is removing your own recovery functions from it. Otherwise you'd have no way to undo the change:

{"error": "self_lockout_blocked",
 "detail": "refusing to disable \"self-service\" in your own profile: it holds their own recovery tools"}

An admin can still disable it for someone else — the guard protects you from yourself, not from administration.

Adding an MCP server

A server must be registered, approved, and granted before anyone can call it. Nothing is reachable by default.

  1. Register it — an admin adds it to the server registry with its upstream URL and owner.
  2. Approve it — a server stays pending until approved. Pending servers are invisible and uncallable.
  3. Register its tools — each tool is registered with a name, version and risk level. A tool with no risk assessment is refused at call time, not silently allowed.
  4. Grant access — an admin grants principals the specific tools they may call, via Roles & grants. Owners can see their own servers under My servers.

Things that will block a new server

  • A localhost or private-range upstream is refused unless the server row explicitly opts in with an allowed CIDR. This stops a server being pointed at internal services it shouldn't reach.
  • Every callable tool needs a credential enrolled, even a placeholder. A missing credential is a denial, not "this tool needs none".
  • Backends must not be reachable except through the gateway. A server that can be called directly bypasses every check on this page.

Choosing an auth mode

Set per server when it's registered — see Identity providers.

Auth modes
ModeUse when
shared_passthroughThe backend accepts your platform identity token as-is
shared_exchangeThe backend needs its own IDP, and your IDP supports token exchange
dedicated_portThe backend needs its own IDP and there's no token exchange. That IDP gets its own port, so one awkward provider doesn't disrupt sign-in for everything else.

When a call is denied

Denials return a short reason. The common ones:

Deny reasons
ReasonWhat to do
unauthenticatedMissing, expired or invalid token. Sign in again.
entitlement_missingNot granted, or disabled in your own profile. Check My access first, then get_profile.
no_grantYour role doesn't meet the tool's requirement. Ask an admin.
quarantinedThe security team has quarantined it. See Quarantine.
rate_limitedToo many calls. Slow down and retry.
taint_floorThe tool isn't trusted enough to call. It likely needs a risk assessment.
policy_deniedA policy rule refused it. The specific rule is recorded in the audit log — see Policy decisions.
dependency_unavailableA required service is unreachable. The platform denies rather than guessing — this is not something you can work around.

Every call, allowed or denied, is written to the audit log with its reason. The security team can look up any request by its id under Audit.
